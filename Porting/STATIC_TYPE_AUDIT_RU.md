# Статическая сверка привязок C# ↔ Java, шаг 7

Проверка исходников `SongsOfSyx-sources(8).jar`, C# и мест вызова. Это разбор кода, а не выполнение игрового сценария. Записи ниже **не** повышают статус типов до проверенного совпадения поведения: в `reviewed_type_bindings.json` по-прежнему только четыре ранее проверенные привязки.

| Java → C# | Установлено по коду | Остаётся до подтверждения переноса |
|---|---|---|
| `settlement/room/main/util/RoomInitData.java` → `SyxDataParser` | Ложный кандидат удалён из старого манифеста, реестра и индекса типов. Java `RoomInitData` хранит пути/ключ комнаты и создаёт `Json`; C# `SyxDataParser` разбирает токены. `OriginalGameData.LoadRooms` остаётся непроверенным файловым кандидатом. | Отдельно проверить загрузку комнат и создание `Json` через `RoomInitData`. |
| `snake2d/util/file/JsonValue.java` → `SyxDataParser`, `SyxDataNode` | Точный источник синтаксического разбора найден в `JsonValue.Reader`/`JsonValueJson`; создана **только файловая кандидатная привязка** для обоих C# типов. У `JsonValueJson` карта `KeyMap` различает регистр ключей и отвергает дубликаты; C# парсер теперь тоже использует `StringComparer.Ordinal` и `TryAdd` с ошибкой. Сопутствующий `Json.bool` принимает лишь строчные `true`/`false` и отвергает иные значения; `SyxDataNode.Boolean` приведён к этому правилу. | `ReadToken` ещё отличается от `Reader` в кавычках, escape, пробелах ключей и завершении значений; нет нормализации строк `JsonValueString` (`%r%`, переводы строк), наложения данных и полного аналога числовых ошибок `Json`. Потребитель `OriginalGameData` есть, точное совпадение разбора всех файлов не доказано. |
| `settlement/entry/Immigration.java` → `ImmigrationRuntime`, `RaceImmigrationState` | Исправлены порог 0.5→0.9, начисление таймера с учётом секунд в дне, вычитание `onTheirWay` из привлечённых и лагерных жителей, раздельная лагерная скорость, отсутствие ограничения счастья в ветке нулевого ожидаемого населения и исключение `population.max == 0` для auto-admit. Исправлена отрицательная верхняя граница при переполненном лимите. | `StandingCitizen.expectationPop` в Java равен `POP.tot` граждан данной расы, но вход C# пока не подключён к этому счётчику. `SettlementEntryRuntime.UpdateImmigration` не вызывается в игровом цикле; `ShouldEmigrate` не вызывается. Внешние источники `StandingCitizen.expectationPop`, `HAPPI`, лагерного `replenishPerDay` и `fullPow` пока не подключены. `currentPopulation` не содержит все группы Java `POP.next` (армия, родители и др.). Ограничение `standingPower` снизу до 0.01 в C# отличается от исходника. |
| `settlement/maintenance/MConsumption.java` → `MaintenanceConsumption` | Java поддерживает грязные чанки 32×32, пропускает отключённые клетки и округляет ресурс в каждом чанке вверх с масштабом 16384. C# раз в секунду суммирует оценки комнат и дорог без этих условий. `All` теперь передаётся в `RoomSystem.ScheduleFacilityWork` для планирования запасов дворников. | Нет разметки отключённых клеток, округления по чанкам и всех оригинальных видов ремонта. `EstimateGlobal/Raw` не читаются, скорость обслуживания от `BOOSTABLES.CIVICS().MAINTENANCE` не подана дворникам. |
| `settlement/room/infra/gate/ROOM_GATE.java` → `GateRuntime`, `GateRuntimeInstance` | Java `lock(tx,ty,lock)` блокирует клетки **конкретного предмета** мебели и вызывает `updateAvailability` для каждой; C# держит флаг **всей комнаты** в памяти. `RoomSystem` вызывает только `Gates.Synchronize`. | `SetLocked` и `CanSubjectPass` не вызываются вне `GateRuntime`; блокировка не влияет на поиск пути и не сохраняется в данных клетки. Нельзя подключать комнатный флаг к путям как аналог поблочной Java блокировки. Оба типа остаются неполными кандидатами. |
| `game/events/disaster/EventAccident.java` → `WorkAccidentRuntime` | Долг начисляется вне смены, как в Java. Бонус безопасности титулов теперь стоит в знаменателе долга, как исходный civic boost; раньше он ошибочно умножал частоту происшествий. Время без кандидатов больше не откладывается для будущего сканирования. | Java сканирует **все** room blueprints с коэффициентом их общего количества, C# перебирает только активных кандидатов с коэффициентом их числа. При неизменном наборе это компенсируется частотой обхода, но последовательность и изменение набора остаются другими. Для события C# всегда выбирает первый экземпляр комнаты и ближайшего к его якорю жителя; Java выбирает экземпляр по числу работников и проверяет их трудоустройство. Другие источники civic boost ещё не подключены. |
| `settlement/entity/humanoid/ai/home/AIModule_Home.java` → `HomeBehaviorRuntime`, `HomeActivity` и `CitizenSystem` | Исправлена связь завершения пути с домашним состоянием: план заканчивается, если житель не дошёл до service cell; не спящая раса после пути переходит в `StayingHome`, а не в состояние сна. | Исходник выбирает дом/камеру, проверяет приоритеты врагов и комендантского часа, использует стабильное значение `STATS.RAN`, личный час начала дня, дневной свет и случайные действия у кровати. C# подставляет `citizenId*31`, время от полуночи и детерминированную общую длительность. Эти типы являются частичной адаптацией, не точным переносом AI. |
| `settlement/room/health/asylum/ROOM_ASYLUM.java` → `AsylumRuntime` | Пустой `Tick` и его вызов удалены: метод `ROOM_ASYLUM.update(ds)` в исходном Java также пуст; остальные операции C# выполняются через `Synchronize`, `Schedule` и `Reconcile`. Для отсутствующего приюта `TreatmentFactor` теперь возвращает исходный 0, а не 0.25. Снято исключение из проверки явных заглушек. | Отдельно от пустого метода Java `AsylumInstance.updateAction` вызывает `jobs.searchAgain()` и `consumtion.updateRoom(this)`; соответствие C# постановки задач и расхода ресурсов экземпляра ещё не доказано. |
| `settlement/maintenance/MFloor.java` → `RoadMaintenanceSystem` | Исходный `degrade` и `resRate` исключают непроходимые клетки и комнаты. C# теперь не начисляет износ заблокированным дорогам и исключает заблокированные и занятые комнатами клетки из расчёта спроса на ресурс. | Вероятностное начисление износа Java и накопление дробного долга C# различаются; также не сверены все условия пригодности дороги к обслуживанию. |
| `settlement/room/infra/janitor/BITS.java`, `JM.java` → `JanitorRuntime` | В Java целевой запас `maxAm` использует `MAINTENANCE.estimateGlobal(resource)`, включающий дорожное обслуживание; C# теперь получает общий агрегат комнат и дорог, а не только расчёт комнат. | В Java оценка дополнительно умножается на civic maintenance speed и ресурс ищется среди ближайших подходящих работ. C# запас основывается на приближённом глобальном спросе без этого множителя и локального списка работ. |
| `settlement/room/main/job/JobPositions.java` → `RoomJobPositionsRuntime` | Успешная позиция остаётся текущей, `alwaysNew` сдвигает курсор до обхода. Удалён соседний поиск из другого Java менеджера. При поиске C# теперь проверяет переданный вызывающим кодом набор `jobResourceBitToFetch()` и пропускает работу, если все требуемые ресурсы помечены недоступными. `ReportResourceMissing` больше не сбрасывает `hasSearchedAll`, как в Java. | Ни конструктор, ни `Find` пока не вызываются из остальных C# классов: реальные вакансии комнат проходят через другой диспетчер. C# требует от будущего потребителя точного набора ресурсов; поиск и резервирование комнатных работ ещё не интегрированы. Java `reportResourceMissing` немедленно возвращает следующую работу, тогда как C# метод её не возвращает. |
| `settlement/room/main/job/JobIterator.java` → нет проверенного C# кандидата | Удалена ложная файловая привязка к `RoomJobPositionsRuntime`: Java использует обход двумерной области, случайный начальный курсор, соседние вакансии и проверку достижимости ресурса из координат работы. Эти правила не принадлежат `JobPositions`. | Реальный потребитель/эквивалент `JobIterator` в C# не найден; в реестре источник теперь `NotStarted`. |
| `settlement/room/infra/builder/ROOM_BUILDER.java`, `BuilderInstance.java` → `BuilderInfrastructureRuntime`, `BuilderInfrastructureInstance` | Java хранит радиус в знаковом `byte`, а C# принимал положительные радиусы до 255; верхняя граница исправлена на 127. `RoomSystem.UpdateStates` уже использует предел 20 работников и потребность в одном работнике. | `RoomSystem` вызывает только `Synchronize`. Внешних вызовов `Covers` и `SetRadius` нет. Java `WorkBuilder` передаёт координаты конторы и радиус в `SFinderJob.findOnlyJobForced`, который проверяет достижимость по путям; C# `Covers` считает расстояние по клеткам и не участвует в назначении работы. |
| `settlement/room/main/placement/PlacerDoor.java`, `RoomPlacer.java` → `RoomPlanner` | `RoomPlanner.ToggleDoor` реально вызывается и делегирует в `RoomPlacementRuntime.ToggleDoor`, который проверяет наличие клетки в периметре и записывает историю. | Java при редактировании дополнительно проверяет `UtilWallPlacability.wallCanBe`; C# при добавлении двери этого не делает. Условия строительства прохода/стены по типу местности и работам требуют отдельной сверки; не повышать статус файлового кандидата. |

Режим последующей проверки: сопоставление точного Java класса и метода, чтение потребителей и сохранения состояния, фиксация реального отличия. Не превращать наличие класса или файлового кандидата в доказательство работающей связи.
