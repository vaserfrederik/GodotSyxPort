# Godot Syx Port A84

Проект полного поэтапного переноса городской игры на Godot 4 .NET.

## Запуск

1. Установить Godot 4.4 .NET или совместимую версию Godot 4 .NET с .NET 8 SDK.
2. Открыть `project.godot` в Godot.
3. Дождаться восстановления NuGet-пакетов и запустить сцену (`F6`/`F5`).

## Что уже работает

- полностью C#-маршрут запуска: главное меню → новая игра → выбор расы и региона → поселение;
- процедурная глобальная карта с выбором пригодного незанятого региона;
- выбранный регион определяет климат, воду, плодородие, рельеф, залежи и расу первых жителей;
- возврат из поселения на глобальную карту и продолжение текущего поселения;
- `Continue` восстанавливает мировую сессию и поселение из сохранения версии 36, включая точный
  рельеф глобальной карты, сделанные в редакторе изменения и координаты столицы;
- глобальная карта использует исходные атласы земли, воды, гор, леса, рек и поселений,
  отображает туман войны и движущиеся мировые сущности;
- горы собираются из исходного `Mountain.png` по соседним клеткам и высоте вместо повторения
  одного фрагмента; сведения о месте столицы открываются возле курсора;
- в настройках закреплены русский и английский языки, русский выбран по умолчанию;
- карта поселения раскрывает выбранные 3×3 мировые клетки через исходную центр-взвешенную
  интерполяцию; горы, берега и лес больше не повторяют квадрат мировой клетки;
- земля, вода, горные кромки, камни и лесные группы 1×1/2×2/3×3 собираются из оригинальных
  settlement-атласов в одну текстуру, без Node на каждую клетку;
- генерационные дороги и входы создаются до появления жителей и не становятся их заданиями;
- миникарта всегда показывает все 768×768 клеток, а рамка показывает текущее окно камеры;
- камера использует исходные 32 клетки/с, ускорение 48 клеток/с² и масштабирование скорости
  при отдалении; средняя кнопка мыши перемещает карту;
- посольства производят ограниченные очки эмиссаров для поддержки регионов, лести и саботажа;
- договоры требуют мнения и доверия, дипломатические дары расходуют казну;
- мирные NPC-дворы содержат до четырёх наследников и продолжаются после смены правителя;
- 3D-карта 768×768 с клеткой 1×1 м;
- плотное хранение логических клеток без Node на клетку;
- пакетная отрисовка стен через MultiMesh по чанкам 32×32;
- ортографическая камера с видом 90°;
- движение камеры WASD/стрелками и масштабирование колесом;
- постановка задания на строительство стены левой кнопкой мыши;
- инструменты стены, дороги и рабочей зоны;
- инструмент дороги переключает исходные типы клавишей `C`; их стоимость и скорость читаются из `init/settlement/floor`;
- планирование комнаты: область, автоматические стены, проёмы и подтверждение строительства;
- типы комнат Storage, Workshop и Bakery с переходом в Operational после постройки;
- мебель/рабочие объекты строятся жителями (`F`), тип комнаты меняется `Tab`;
- очередь jobs и назначение свободного жителя;
- поиск пути по клеткам с обходом построенных стен;
- житель подходит к соседней клетке, выполняет работу и возводит стену;
- минимальный счётчик жителей, заданий и стен.
- фиксированный simulation tick и скорости времени;
- базовое сохранение/загрузка (`Ctrl+S` / `Ctrl+L`).
- разборка выбранной комнаты клавишей `Delete` с очисткой jobs, складов, мебели и зависимых регистраций.
- 64 жителя симулируются как data-объекты и выводятся одним MultiMesh, без Node на жителя.
- строительство резервирует и расходует материалы.
- рабочий физически получает зарезервированный стройматериал, несёт его на площадку и только после доставки начинает работу;
- один обычный рейс ограничен исходными 6 единицами; крупная стройка и перевозка штабеля выполняются несколькими рейсами;
- завершив стройку, рабочий сначала продолжает совместимую соседнюю работу в порядке направлений оригинального `PlanOddjobber`;
- обычный поиск работы ограничен исходными 250 клетками, что исключает назначения через всю карту 768×768;
- доставленный материал хранится в прогрессе job и выпадает на клетку при отмене строительства;
- Bakery использует исходный rate 6 Grain + 1 Wood → 6 Bread/Food; Carpenter — 2 Wood → 0.5 Furniture;
- производство выполняет исходный 45-секундный цикл и накапливает дробные rates на уровне комнаты, выдавая целые ресурсы только при пересечении границы;
- runtime знает все 42 оригинальных resource keys; дополнительные исходные рецепты Bakery/Carpenter переключаются клавишей `V` после выбора комнаты через `I`;
- сырьё производства физически переносится профильным работником из Storage к workstation партиями до 15 и хранится локально до 31 единицы каждого входа;
- production-job появляется только после доставки хотя бы одной единицы каждого требуемого ресурса;
- production jobs создаются только у полностью Operational-комнаты с завершённым строительством,
  выходным хранилищем, рабочим местом и доступной соседней клеткой; при потере готовности jobs отменяются;
- production supply резервирует сырьё в конкретном stockpile и физически переносит его к workstation;
  готовый продукт резервирует место в конкретном stockpile и переносится туда партиями до 6;
- loose resources резервируют место конкретного stockpile и становятся его физическим содержимым
  только после доставки; UI заполненности читает состояние stockpile runtime напрямую;
- stockpile принимает только ресурсы с выделенными ящиками; для каждого ресурса задаются число
  ящиков и лимит на ящик, а fetching и priority управляют созданием и порядком hauling jobs;
- production cycle атомарно проверяет все входы и заранее резервирует room storage для каждого
  выхода; дополнительные outputs больше не обходят reservations, а реальный overflow остаётся грузом;
- layouts сохраняют исходные tile-data роли `WORK/JOB` и `STORAGE/CRATE`; производство и штат
  считают только точные workstation-клетки после поворота мебели, а не весь furniture footprint;
- каждый furniture layout сохраняет раздельные `multiplierCosts` и `multiplierStats`, включая
  дробные значения; строительная цена и параметры комнаты больше не используют общий округлённый множитель;
- maintenance использует исходный `brokenResourceAmount` конкретной furniture-клетки и вероятность
  материального ремонта из `MRoom`; требуемая единица ресурса физически резервируется и доставляется рабочим;
- поломка одной клетки переводит весь атомарный furniture footprint в broken-состояние: его
  workstation/storage отключаются, комната останавливается, а repair-job восстанавливает объект целиком;
- `FurnisherStat` вычисляется в исходном порядке: raw item totals преобразуются через relative,
  efficiency и employees-relative формулы и используются service, school, hospitality, law и production runtime;
- commit планировки проверяет извлечённые из Java `flush(min,max,rotations)` границы каждой
  furniture group и `FurnisherStat.min`; недостаточная или избыточная обстановка не создаёт jobs;
- голод проверяется 16 раз за исходный 1152-секундный день с базовой вероятностью `RATE: 0.5`;
- голод перенесён по исходным `StatsNeeds/AIModule_Food`: уровни 0–64 с шагом 16 и приоритетами относительно работы;
- со второго уровня житель прерывает работу, идёт к складу, берёт одну еду и ест 8–20 секунд;
- при отсутствии складской еды житель резервирует ближайшую лежащую Food и идёт к ней; перевозчики не могут забрать зарезервированную единицу;
- на уровне starvation житель прекращает обычную работу, повторяет поиск пищи и визуально отмечается красным;
- максимальный голод приводит к смерти от истощения; состояние жителя и незавершённое принятие пищи сохраняются;
- позиции и потребности жителей входят в сохранение.
- дальние маршруты используют двухуровневый pathfinding по регионам 32×32;
- jobs выдаются из ближайших региональных очередей с ограничением числа A* на tick.
- произведённые товары появляются как грузы в мире и доставляются жителями в рабочий Storage;
- площадь Storage задаёт вместимость, а незавершённая перевозка и поднятый груз сохраняются без потери ресурса.
- рабочие автоматически получают профессии Baker/Carpenter по числу действующих комнат;
- производственные задания доступны только нужной профессии, специализация сохраняется;
- профессии и переносимый груз различаются цветом в общем MultiMesh жителей.
- job-board обслуживает приоритеты Production → Hauling → Furniture → Construction → Road внутри ближайших регионов;
- `F7/F8` уменьшают/увеличивают лимит пекарей, `F9/F10` — ремесленников;
- лимиты штата и приоритеты незавершённых заданий входят в сохранение версии 3.
- `I` включает выбор комнаты кликом; `F11/F12` меняют её индивидуальный штат;
- каждое построенное рабочее место может создать отдельный производственный job;
- уменьшение штата отменяет лишние jobs и возвращает зарезервированное сырьё;
- индивидуальные лимиты комнат входят в сохранение версии 4.
- черновик комнаты отображает площадь, будущий периметр и проёмы отдельными цветами;
- draft не изменяет постоянные tile-данные до подтверждения `Enter`;
- панель выбранной комнаты показывает состояние, площадь, стены, рабочие места, штат и рецепт.
- активные маршруты хранятся в общем `SharedPathPool`; жители держат только числовой handle;
- буферы путей арендуются через `ArrayPool`, что снижает давление GC при тысячах жителей;
- экономика хранит до 120 минут истории производства и расхода по шести ресурсам;
- экономическая панель показывает остатки и поток за последнюю минуту;
- сохранение версии 5 включает историю экономики и накопленные итоги;
- запись сохранения выполняется через временный файл и резервную копию; повреждённый основной файл восстанавливается из backup.
- каждые пять минут активной симуляции создаётся автосейв с ротацией трёх слотов;
- цепочка загрузки: основной save → backup → autosave 1–3.

Полный предоставленный C#-экспорт находится в `LegacySource/`. Он включён в архив для трассировки, но исключён из компиляции через `GodotSyxPort.csproj`: классы подключаются к рабочему коду только после семантической адаптации.
Статус каждого из 2 465 файлов записан в `Porting/legacy_compile_manifest.json`; проверенные адаптации собираются из `Scripts/LegacyCompat` и целевых подсистем.

Предоставленные деревья `init` и `text` (890 файлов) лежат без изменения в `Data/Original` и читаются при старте через `SyxDataParser`. Инвентарь и уже подключённые исходные значения перечислены в `Porting/ORIGINAL_DATA_INVENTORY.md`.

Трассировка каждой перенесённой механики до Java-класса и явные границы адаптации записываются в `Porting/SOURCE_TRACE.md`.
Параметры, которые Java загружает из отсутствующих внешних JSON, перечислены в `Porting/EXTERNAL_DATA_REQUIRED.md`; временные значения не считаются оригинальными.
Текущая оценка готовности по уровням и перечень крупных оставшихся этапов находятся в `Porting/PROJECT_ESTIMATE.md`.
